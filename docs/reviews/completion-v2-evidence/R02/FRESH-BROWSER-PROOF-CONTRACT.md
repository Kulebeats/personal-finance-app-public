## Decision and scope

The smallest trustworthy **fresh-browser application** proof is one synthetic registration in browser A, the exact URL decoded from its actually accepted SMTP message opened in an independent browser B, the actual verification page/API transition, and independent DB/session readback before login. It must use the real application entry/middleware/client, real CSRF policy and unchanged limiters. A hand-built Express router, mock email function, fabricated verification page, database-derived token or direct fixture verification UPDATE cannot substitute for any link in this chain.

This proof currently cannot execute: the accepted R20 manifest explicitly sets runtimeDependencyIdentity/executionAuthorized false and prohibits application launch until a separately reviewed installed-dependency bytes/resolution/custody contract is accepted. Calling the same app imports a “component” would bypass that gate; NODE_ENV=development to enable CSRF/limiters would not resolve it and would change production cookie behavior. This document grants no exception. Implementation of R02 source and ordinary protected regression tests can be allocated separately, but production browser acceptance waits for the dependency and full-profile boundaries below.

A separately scoped **mail-transport component** remains an unaccepted preparatory alternative: exercise actual `server/services/emailService.ts` sendEmail against an owned authenticated numeric-loopback SMTP sink in a non-test isolated child, with in-memory synthetic input and no app/auth/DB imports. That module uses its actual Nodemailer getTransporter configuration and disableFileAccess/disableUrlAccess. The exact proposed files, dependency projection/custody, bounded AUTH/MIME protocol, immutable transport controls, evidence and negative controls are in `MAIL-READINESS.md`. Its alternatives assessment recommends prioritizing shared full-application dependency/runtime custody: the seven-file component does not unblock R02 and may duplicate that harness. It can prove only this compiled service transport configuration, raw MIME capture and sanitized logs, not token issuance, the initial registration template, route reachability, CSRF, session or fresh-browser verification. Any implementation requires demonstrated value/feasibility, independent design review, parent adjudication and a separate exact-file/run-allocation amendment. A separately authorized component need not wait for unrelated full-profile Redis/browser/PG/application dependency-custody prerequisites, and cannot clear them. Using NODE_ENV=test is unsuitable because getEmailConfig returns null there. No “partial J01 pass” follows from this component.

Invalid-token readback compares semantic identity fields, not a blanket count of every session-store write. If the selected CSRF solution persists anonymous state, allow only anonymous CSRF/session establishment without userId, MFA-pending identity or credential generation; a valid existing session may have its expiry touched, and scheduled expiry pruning may remove already-expired transport rows. Record and classify these separately from token effects. They must not create/promote/switch an authenticated or pending-MFA subject, change its payload/security generation, create/change tracked identities or revocation tombstones, or consume/alter a verification challenge on failure. `GuardedSessionStore.persist(..., touch=true)` currently updates the session expiry, so forbidding every session write would incorrectly reject ordinary completed requests. A changed identity is never excused as housekeeping.

Expiry negatives may create a separate synthetic expired challenge only under reviewed fixture authority; explicitly label that as expiry guard evidence, never mail issuance evidence. Prefer configured test-only issuer clock DI exercised in repository tests, while actual browser expiry uses a separately authorized fixture update or real wait recorded honestly.
