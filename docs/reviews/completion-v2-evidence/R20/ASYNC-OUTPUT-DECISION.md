## Why asynchronous writes need a different expiry path

Windows stdout pipe writes through `process.stdout` can block the JavaScript thread. Callback-based `fs.write` instead uses the filesystem worker pool, allowing the main event loop to service the deadline. This is supported by the exact [Node 24.22.0 process documentation](https://raw.githubusercontent.com/nodejs/node/v24.22.0/doc/api/process.md), [filesystem documentation](https://raw.githubusercontent.com/nodejs/node/v24.22.0/doc/api/fs.md), and [Windows filesystem implementation](https://raw.githubusercontent.com/nodejs/node/v24.22.0/deps/uv/src/win/fs.c).

**Do not combine a pending async filesystem write with `process.exit(1)` as the cancellation mechanism.** The pinned default exit handler invokes `uv_library_shutdown`, which calls thread-pool cleanup; that cleanup joins workers, including a worker potentially blocked writing to the unread pipe. This is a source-derived risk, not a newly executed reproduction. See [Node default exit](https://raw.githubusercontent.com/nodejs/node/v24.22.0/src/api/environment.cc), [libuv shutdown](https://raw.githubusercontent.com/nodejs/node/v24.22.0/deps/uv/src/uv-common.c), and [worker joins](https://raw.githubusercontent.com/nodejs/node/v24.22.0/deps/uv/src/threadpool.c).

The accepted expiry mechanism is the public `process.kill(process.pid, 'SIGKILL')`, restricted to this process and the post-cleanup output boundary described below. The pinned native kill binding first runs registered native AtExit callbacks, then calls `uv_kill`; it does not enter the default exit handler above. Windows libuv maps this signal to `TerminateProcess(handle, 1)`. This is not a claim that arbitrary addons or embedders have bounded AtExit callbacks: the fixed clean runner must retain its existing source closure, with no selected-package evaluation, addon or preload. See [native kill binding](https://raw.githubusercontent.com/nodejs/node/v24.22.0/src/node_process_methods.cc), [AtExit delegation](https://raw.githubusercontent.com/nodejs/node/v24.22.0/src/api/hooks.cc), [callback iteration](https://raw.githubusercontent.com/nodejs/node/v24.22.0/src/env.cc), and [Windows kill implementation](https://raw.githubusercontent.com/nodejs/node/v24.22.0/deps/uv/src/win/process.c).

Windows termination requests cancellation of pending I/O and terminates all process threads; process completion still depends on pending I/O completing or being canceled. Therefore source inspection supports this design but does not replace the actual pinned-host pipe control. See [Microsoft TerminateProcess contract](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess).

## Required implementation contract

1. Keep the original absolute deadline established before stdin. No new timeout option, reset budget, additional process, source-closure member or dependency is approved. The existing runner and its existing regression file are the intended changed files within the accepted nine-file slice; `node:fs` is a builtin import.
2. Enter output only after the awaited command settles and its native children, metadata children and retained descriptors have finished cleanup. Input expiry retains its input-close behavior. Work expiry only marks exhaustion and lets existing helpers finish their bounded cleanup. Never use the self-kill path during input, collection, observation or cleanup.
3. Encode the returned canonical string once as UTF-8. Recheck its existing **8 MiB byte bound**, preserve the bytes exactly, and emit no extra framing, partial-success record or fallback report. Keep that buffer alive and immutable until its callbacks finish.
4. Use callback `fs.write(1, buffer, offset, length, null, callback)` with at most **64 KiB per submission and one outstanding write**. Advance by the actual positive integer byte count. Reject zero, negative, noninteger or greater-than-submitted counts, callback errors and synchronous dispatch exceptions. Do not retry zero progress, silently skip bytes, schedule overlapping writes or retry errors indefinitely. Check the same absolute deadline before every submission and after every callback.
5. Track outstanding-write state explicitly. While the output write is outstanding, the original deadline callback invokes self-only `SIGKILL`; it must not await a write callback, close fd 1 concurrently, call `process.exit`, or run another output operation first. Only the current process PID is permitted; no caller-supplied PID or process group. There is no public termination capability exposed by this implementation detail.
6. Callback errors, zero progress and other refusal paths may use ordinary nonzero shutdown **after the callback has completed and no async write remains pending**. Likewise a deadline detected between writes can refuse normally. Never reject an output promise early and clear its only deadline while leaving a pending write alive. A self-kill failure cannot be treated as successful enforcement; keep that host/candidate held if the actual control cannot terminate it.
7. Success requires acknowledgment of every output byte, no pending write, and a final nonexpired-deadline check. Only then mark done, clear the deadline and allow normal successful exit. A partial report followed by failure is never an accepted report, even if a prefix happens to parse.
8. Do not introduce another synchronous stdout/stderr path through error handling, console output or exit listeners. The preferred minimal refusal path is silent nonzero exit; the fixed generic stderr diagnostic may be omitted. If retained, it must use an equally bounded async operation after resource cleanup under the same remaining deadline, and needs its own blocked-stderr control. There is no new stderr allowance or fresh timeout. Do not print raw inputs, paths or exceptions.
