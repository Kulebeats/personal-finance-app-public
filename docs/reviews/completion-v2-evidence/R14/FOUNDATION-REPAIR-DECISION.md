## 1. Inactive versions and immutable replay conflicts

Accept the proposed uniform rule. After generic closed request validation and definition lookup, an inactive caller version returns `UNSUPPORTED_DEFINITION_VERSION` before invoking any SQL or transaction. Do not query whether its due identity already exists. A request with an invalid generic shape can still receive its ordinary shape error; uniformity applies to otherwise structurally valid inactive-version requests. Do not run the active version's definition-specific payload validator as if it were the inactive version's schema.

For an active caller version, due-kind and definition-specific input validation must finish before SQL. Only an admitted request reaches INSERT ON CONFLICT / separate SELECT. Any differing stored immutable field then produces `DUE_IDENTITY_CONFLICT`, including an item stored under an older version when the code-owned registry now admits a newer version. Identity uniqueness still excludes definition/policy versions; neither conflict path inserts a second item, resets progress or invents an upgrade policy. An old stored definition remains unclaimable by the new registry until a separate reconciliation decision.

Append this as an explicit clarification to the accepted statement that immutable mismatches conflict: that statement applies after request admission. Required controls:

- A spy executor whose SQL and transaction methods fail if called: structurally valid inactive-version requests, including payloads invalid under the active definition, uniformly refuse with zero calls.
- The same inactive request refuses identically for absent, present and concurrently uncommitted identities; no SQL means no lock/timing dependency. Existing rows remain byte/semantic unchanged.
- Active-version invalid payload refuses before SQL. Active V2 registry versus an existing valid V1 item yields conflict, not unsupported caller version or a duplicate. Same-version changed policy also conflicts.
- Preserve concurrent admitted identical/conflicting enqueue controls and terminal replay readback.

## 2. Claim/attempt integrity: local constraints plus transactional refusal

The minimum coherent foundation uses **explicit corruption refusal**, not a new circular deferred foreign key. SQL enforces the row-local invariants; every foundation mutation checks cross-table ownership under locks. Independently authored SQL can still create an orphan running item that passes local CHECKs, so neither documentation nor tests may claim the schema independently proves attempt existence. Such rows must cause a closed `INVALID_STORED_CLAIM`-style refusal with complete transaction rollback, never an expiry, heartbeat, effect or successful completion. No automatic repair/adoption is added.

Keep the existing attempt-to-item restrictive FK and unique item/generation and item/token constraints. Add aligned schema/draft CHECKs, with explicit null handling:

- A running item has generation greater than zero, claim_count equals generation, all required owner fields, and finite `claimed_at < lease_until`. Nonrunning claim fields remain null.
- An attempt has finite claim/heartbeat timestamps, `last_lease_at >= claimed_at`, and, when finished, finite `finished_at >= last_lease_at`. Running means unfinished, no after-checkpoint or error; finalized means finished and a nonnull after-checkpoint not below before-checkpoint. Preserve registered outcome/code validation and current byte bounds.
- Do not put a current-clock lease-validity condition into a CHECK; legitimate leases must be allowed to expire. Use fresh database time in operations.

After locking the item, lock its current attempt in the same transaction, in **item then attempt** order. Require exactly one matching item ID, generation, token, worker, claim timestamp, running outcome, unfinished state, and checkpoint-before matching the current item checkpoint version. Validate this before renewal, expiry/failure/unknown transitions, private fence creation or callback invocation. `assertJobFence` must not certify a claim whose matching attempt has disappeared or changed. Maintain the attempt lock through the operation.

All renew/finalize attempt UPDATEs must use exact ownership plus running/unfinalized predicates and RETURNING, and assert exactly one affected row. All corresponding item mutations also assert exactly one. A missing, mismatched or already finalized attempt is corruption refusal, distinct from an ordinary stale caller token; roll back the entire transaction. The final effect transition must reassert attempt coherence after the callback and before returning. It must roll back item, synthetic effect, checkpoint, result and attempt together if any final check fails. This catches a callback that damages its own attempt even though outside transactions are excluded by the retained lock.

Compare timestamps in SQL at database precision. The current claim path writes item time with `clock_timestamp()` but inserts attempt time through a returned JavaScript Date, losing microseconds. Create the attempt using INSERT ... SELECT from the just-claimed item, or reuse one database timestamp entirely inside SQL. Do not introduce a false mismatch through JavaScript millisecond equality or weaken equality to conceal it. Reuse a fresh post-lock DB timestamp coherently where chronology fields are updated; never a pre-wait timestamp as lease authority.

Why no deferred composite FK now: it would require a referenced composite unique key and a nullable current-attempt relationship, circular insertion ordering, explicit deferrability and schema/journal/snapshot representation. It would prove referenced tuple existence but not by itself prove running outcome, chronology or all transition semantics. That is extra migration machinery rather than a substitute for the checks above. PostgreSQL explicitly distinguishes row-local CHECKs from cross-table constraints. See [PostgreSQL constraints](https://www.postgresql.org/docs/18/ddl-constraints.html). If parent requires arbitrary SQL writers to be unable to commit an orphan running item, this bounded-refusal choice is insufficient and a separate exact deferred-FK/constraint-trigger design must be reviewed before application; do not silently imply that stronger guarantee.

Required controls: direct SQL generation-zero and incoherent chronology inserts/updates fail; otherwise locally valid orphan/mismatched/finalized-attempt fixtures are explicitly allowed to be constructed only by owned test SQL, then every store mutation refuses without changes. A fenced callback must not run for pre-existing corruption. Corrupt/delete the matching attempt inside a synthetic callback after writing an effect: final enforcement refuses and rolls back all writes, restoring the original attempt. Verify fractional-second item/attempt equality from SQL, successful normal renewal/completion, and exact-one history under concurrent transitions. Test cleanup removes attempts before items; do not weaken production constraints for fixtures.

## 3. Deterministic selection, bounds and indexes

Choose **one unified eligibility order**, preserving the current candidate's order: `eligibility_at ASC, due_at ASC, id ASC`, where `eligibility_at = coalesce(lease_until, ready_at)` for active rows. Local state constraints make that lease expiry for running rows and ready time for queued/retry_wait rows. Clarify the accepted ready-time wording to include expiry this way. Do not introduce ready-first, expiry-first, alternating streams or per-job priority; those would change ordering/fairness.

The simplest matching index is a partial B-tree on `(coalesce(lease_until, ready_at), due_at, id)` for states queued/retry_wait/running. Use that same expression and literal active-state predicate in selection, with the requested job-name filter. Replace the unsupported combined OR/order dependency on separate ready/expiry indexes. A separately justified job-leading counterpart may help single-name queries, but is not a substitute for a globally ordered multi-name path. Parent must review exact schema/draft/index parity before assigning/registering final DDL.

Sample one exact DB cutoff for candidate discovery, retaining timestamp precision, and use `eligibility_at <= cutoff` as an indexable range. This cutoff is discovery only. Select `LIMIT requested` with `FOR UPDATE SKIP LOCKED`, requested in 1..100, then recheck state, definition, matching attempt and fresh DB time **after each lock** before transition. No refill loop and no immediate re-claim of an expired row in the same invocation; expiry still finishes its old attempt and preserves backoff. A stale candidate consumes a visit rather than triggering unbounded replacement search.

The limit bounds locked/processed candidate items, including expired items without a new claim. It does **not** bound all PostgreSQL index entries, MVCC versions or locked/nonrequested rows examined. SKIP LOCKED and filtering can require additional physical inspection; statement/lock/transaction timeouts bound that work. If the requirement were literally at most100 physical inspections, neither the existing query nor a two-stream merge can promise it while also finding the first100 unlocked eligible rows. This distinction must be explicit, not hidden behind `visitedCount`. PostgreSQL documents both ordered index/limit behavior and the inconsistent queue view supplied by SKIP LOCKED: [index ordering](https://www.postgresql.org/docs/18/indexes-ordering.html), [SELECT locking](https://www.postgresql.org/docs/18/sql-select.html).

Use a bounded read-only EXISTS probe after transitions, with a new DB discovery cutoff and the same requested names/active eligibility predicate, for `moreEligible`. Do not lock a 101st item or infer it merely from `visitedCount === limit`. Define it precisely as visible eligible backlog in that probe's statement snapshot, **including rows locked elsewhere**; true is not an immediately claimable guarantee, and false is not a promise about later commits/time. A transitioned retry row is legitimately included if its backoff has elapsed by probe time. No cached pre-transition candidate list, future row, terminal row or unsupported requested name can fabricate true. Separate status still exposes running/locked work.

No ready/expiry starvation is introduced by class priority: both compete by the same total key. For a finite backlog with eventual lock release, repeated calls advance in that order. Do not promise absolute starvation freedom against indefinitely held locks or an endless supply of backdated earlier work; that would require a different admitted scheduling policy. Tests must show eventual service of both classes under a normal later-arriving workload, and the exact dueAt/id tie order across multiple names.

## 4. Protected evidence required after source approval

Retain the existing proposed lock-wait/fresh-clock test; it does not replace a true renewal/reclaim race. Use independently guarded connections and explicit barriers to overlap renewal and expiry scanning on the same claim. Cover both serial orders: renewal holds the item while a scanner SKIP LOCKEDs it, then its extended lease remains live; expiry owns/finalizes the item while renewal contends, then renewal returns stale with no resurrection. At expiry equality, renewal cannot win by using pre-lock time. Assert one old attempt, one failure for expiry, unchanged generation until a later eligible claim, no duplicate finalization, and no active transaction after cleanup. Use bounded wait observation/barriers, not guessed sleeps or an unbounded polling loop.

On the explicitly granted disposable target, seed a substantial owned mix of overdue/future queued/retry rows, expired/live running rows with valid attempts, terminal rows and unrelated names. Capture populated EXPLAIN (ANALYZE, BUFFERS) for actual parameterized selection and EXISTS shapes at one and multiple requested names, including sparse requested names. Require evidence of a usable ordered index path without sorting the entire eligible backlog for LIMIT, and record rows removed/visited and buffers; small empty-table plans or forced planner switches do not qualify. If normal plans still perform broad sort/scan for the intended cardinalities, return for index/query repair rather than declaring the new index sufficient. ANALYZE and execution remain parent-controlled SQL work.

Prove mixed ready/expired limit100 visits, the 101st remaining item, exact-limit/no-other-work false, future-only false, locked eligible backlog true, and no extra row lock taken by the hint. Check under duplicate/permuted requested names and tie timestamps. Preserve the existing101-effect continuation test separately from101 independent queue rows. Run new corruption/constraint negatives and migration parity under the existing protected target contract; no new URL/role/target assumptions or producer admission.
