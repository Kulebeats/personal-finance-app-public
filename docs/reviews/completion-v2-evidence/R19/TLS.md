## Implementation and compatibility

Baseline for this slice is accepted readiness/logging chain through64c95b8 on codex/capital-r19-foundation. Parent owns canonical status and external enablement. Runtime is native Windows ARM64 Node24.22.0; no .env was copied. Source files are server/dbSsl.ts, server/db.ts, server/utils/validateEnv.ts, their focused tests and an explicitly scoped TLS-only child fixture.

Production TLS and certificate verification are now enabled by default, with no DATABASE_SSL=false or DATABASE_SSL_REJECT_UNAUTHORIZED=false production escape hatch. Development remote connections also verify by default. A local development connection can explicitly select DATABASE_SSL=false; ordinary protected test workers use NODE_ENV=test plus PFA_TEST_MODE=unit/database and a numeric/localhost endpoint, yielding explicit ssl:false when no TLS request is present. An explicit verification/CA request is never downgraded by test mode. The existing test manifest/pg guard still owns database identity and write permission; TLS policy is not a substitute for those guards.

The pool no longer receives connectionString because installed pg/lib/connection-parameters.js parses that property over explicit SSL options. It instead receives validated explicit host/port/database/user/password/ssl fields. Standard URLs without options and the existing legitimate sslmode=require /sslmode=verify-full forms are supported; require is intentionally strengthened to full certificate/hostname verification. Unsafe or ambiguous TLS/routing/file/options query overrides and fragments are rejected with actionable static messages. Operators must remove such URL options and configure the explicit CA environment variables. No credential or full URL is included in those errors.

A supplied CA PEM/file must contain parseable CA certificates only; malformed/blank/unreadable/conflicting CA input refuses before pool construction. Without a custom CA, Node's trusted CA store remains active with rejectUnauthorized:true. Startup schema and pool construction share pure policy checks. Actual deployed CA/hostname validation remains OI-01 evidence; no fallback disables verification when that check fails.
