## Erased subjects and restored authentication: quarantine first

An older backup can resurrect a user erased after its cut, deleted object versions, a previous password, verification/reset tokens or revoked sessions. Merely restoring users.erased_at/session_revocations from that same old backup cannot cover later events. Current identity/audit source is a useful primitive, not an independent post-cut replay ledger.

Before any traffic or workers, require a fresh authenticated erasure/security overlay through the incident/recovery watermark. Missing, stale, corrupt or unaccounted-for markers keep the entire restore quarantined. Parent/R07 must define its durable source and key custody; if every copy of the newer authority is lost, recovery does not assume that no erasures occurred. The first A contract can positively state an explicitly verified synthetic no-post-cut-marker case and negatively prove missing/stale/post-cut-marker refusal. It must not substitute a stub for application erasure replay evidence.

Once the R07 replayer exists, apply identity revocation first, monotonic security-generation/revocation reconciliation and canonical pseudonymization/purge rules, preserving other members' legitimate shared/audit history. Never decrease restored security generations or allow a tombstone to authenticate. Reconcile old password/reset/verification material under R01's recovery policy; invalidating session cookies alone does not make an old password safe. All restored sessions/pending MFA sessions and stale download links remain unusable until the reviewed security replay policy permits authentication.

Apply object denial/cleanup for every erased subject and all relevant retained versions before downloads are enabled. Restore mapping must preserve shared-object ownership correctly; unknown ownership blocks serving the object. Erasure completion/retry and legal-hold handling belong to the durable R07 state machine. Do not copy all historical object versions back into service or delete remaining members' shared files as a shortcut. OI-04 controls backup retention/deletion obligations; no legal-compliance claim follows from this plan.

Required B negative fixture: backup before erasure, erase subject after cut, recover the old bundle plus newer overlay, and prove old cookie/password recovery path/token/file denial, pseudonymized retained shared history and retry-safe object cleanup. Also test absent/older overlay and an interrupted replay; both must remain unservable. This fixture is blocked until R07/manifest contracts are assigned and verified.

## RPO/RTO and rollback acceptance

Record UTC timestamps and monotonic elapsed durations for intent approval, incident declaration, artifact/key discovery, target preparation, DB restore, object restore/hash check, security replay, consistency checks and release-gate completion. RTO starts at declared recovery/incident time before preparation; it ends only at verified service readiness after replay, not when pg_restore exits. Report pauses/operator waits separately without silently subtracting them. Bound each child and hard-stop before the total four-hour budget; a small synthetic result does not establish production-volume throughput.

RPO is incident time minus the **last complete recoverable joint DB/object cut**, not backup completion time or scheduler cadence. It must be <=24h. Capture duration, verification lag and failed backups affect that age; a policy saying daily is not proof. A synthetic newer row/object after the cut must be explicitly excluded and counted as deliberate simulated loss. Missing required objects/security overlay makes the recovery point invalid rather than assigning a favorable RPO. External restore acceptance also needs measured representative data volume and operator-controlled keys/accounts.

Rollback is compatibility-first. Keep the restored/candidate schema and data for a code rollback only after the exact earlier code SHA passes the same authorization/security/visibility and data-read/write contract on that schema. Do not automatically reverse migrations or restore an older DB to undo a deploy: that can discard accepted writes, erasures and revocations. If no safe earlier code exists, keep quarantine and forward-fix under a reviewed migration/release plan.

Concrete current hazards: 0011 clears outstanding raw verification/pending-email material for the hashed-token contract; inverse SQL cannot recreate those secrets safely. 0012 adds erased_at/security_generation/session_revocations; code predating the enforced R01 guards is not a safe rollback merely because added columns are nullable/defaulted. The installed Drizzle ORM migrator source wraps pending migration statements/journal inserts in a transaction, but its initial schema/journal setup is outside that transaction; actual drizzle-kit migrate failure/compatibility behavior still needs controlled proof. Never claim every partial DDL/global change is automatically undone.

Before accepting a rollback SHA, test old-code/new-schema and candidate-code/new-schema against the same synthetic restored state, including erased subject and selected-session denial, token hashing, object mapping, constraints and journal hashes. Use a separate marked fork for destructive failure injection; no edits to committed migration files or R01 schema. If the dependency contract changed, record NO-GO/forward-fix rather than inventing an inverse.
