# R05 Profile Persistence Implementation Plan

**Goal:** Make every currently offered Profile Settings control save to the authenticated user's row, read back, and survive reload, including intentional clears, without broadening public profile disclosure.

**Architecture:** Build a typed client patch from changed, offered controls. Validate a bounded server payload, update the subject's `users` row and a minimized audit row in one transaction, and return the existing own-profile DTO. Keep the image upload routes separate. This is one AH-07/SET-01 slice of R05, not closure of the full R05 packet.

**Tech stack:** React Hook Form, Zod, TanStack Query, Express, Drizzle, PostgreSQL, Vitest, and the guarded synthetic database harness.

**Review status:** Astra High approved bounded local implementation with the decisions recorded below. No implementation or persistence evidence is claimed by this document. Source baseline `840233c2` (the profile validation repair entered at `a22e9f18`); canonical evidence checkpoint is now `8f291053`. The master specification at `docs/plans/2026-10-15-master-completion-spec.md:563,1002-1030` is the status and acceptance authority; its AH-07 row is OPEN. `docs/reviews/2026-10-13-independent-readiness-fable/evidence/domain-settings-notifications-ai.md:13` is historical SET-01 evidence, not the current field count.

## Authority and limits

- Local source, schema, and synthetic acceptance work is authorized. This plan creates no authority to write a shared or production database, collect new real-user data, change retention wording, provision external services, merge, or deploy. OI-04 at master-spec line 92 still gates real-user privacy/export/erasure release, legal holds, backup deletion, and sensitive-field necessity decisions.
- The existing `users` columns and `audit_logs` nullable `household_id` are declared in `shared/schema.ts:253-306,2114-2123` and baseline `migrations/0000_youthful_speed.sql:1125-1147`. Do not create a migration for fields already represented. If an explicitly verified disposable target differs, stop and prepare a versioned migration for review; do not use ambient `finance_app` or an imperative `db:push` to reconcile it.
- Keep the separate profile-picture and banner POST/DELETE paths with `householdGuard` (`server/modules/settings/settings.routes.ts:42-69`). Direct profile PUT must never set either stored image URL, even if a stale client includes `profilePicture`, `profilePictureUrl`, or `bannerUrl`.

## Frozen input and clearing rules

1. **Required values.** Preserve the existing client contract: `fullName` length 1–100; `firstName` and `lastName` length 1–50; `gender` is `male | female` (`profileSchema.ts:39-51,82-85`). Their keys may be omitted from a patch, but an included `null` or empty value is invalid. Do not use SQL nullability to weaken the currently required form fields.
2. **Birthday and switches.** `birthday` is client `Date | null`; null is valid despite the current required-sounding message (`profileSchema.ts:57-76`). `birthdayHideYear` is a boolean with default `false` (`:78`). An omitted key leaves the DB value unchanged; an included `false` persists false. Add an explicit birthday-clear path in the UI, since `BirthdayPicker.tsx` presently has no clear control. Resolve the label/message inconsistency against the existing nullable schema, without inventing a new birth-date requirement.
3. **Optional scalar text.** Phone mobile/work accept the current Zambian regex (`profileSchema.ts:13-15,87-103`); home phone is only max 20 (`:104`); occupation max 100 (`:106`); NRC max 20 and, when present, `123456/78/9` (`:212-220`); bio max 1,000 (`:140`). The typed patch maps an intentional empty optional control to explicit `null` for nullable columns. Omission means unchanged. Do not normalize away a provided `false` or numeric string `"0.00"` using truthiness.
4. **Address.** Existing client bounds are line 1 and line 2 max 200, city/state max 100, postal code max 20, and country exactly two characters with default `ZM` (`profileSchema.ts:17-36`). Address line 1 and city carry UI asterisks but are schema-optional (`AddressFields.tsx:100-117,143-151`); do not silently make the API stricter in this slice. Country is a selected/default value, not an optional clearable text field.
5. **Social links.** Four rendered links are optional or empty. Keep the existing LinkedIn/Facebook/Twitter refinements and website URL rule (`profileSchema.ts:142-210`); do not invent a new maximum length or new link policy. The stored object may also contain hidden `github` and `email` keys; a visible-link edit must preserve them.
6. **Financial profile.** `incomeFrequency` is `monthly | bi-weekly | annual`, default `monthly`; `employmentStatus` is `employed | self-employed | retired | unemployed | student | ""`; `investmentGoal` is `retirement | home_purchase | wealth_growth | education | emergency_fund | ""`; `riskTolerance` is `low | medium | high | ""` (`profileSchema.ts:112-131`). Empty optional selections clear; omit means unchanged. Annual income is currently an optional string in Zod and an HTML number input with no explicit `min` or `step` (`FinancialProfileFields.tsx:65-80`), while DB storage is `numeric(15,2)` (`shared/schema.ts:299`). Validate decimal representability exactly as a string: at most 13 integer digits and at most two fractional digits under the column's precision/scale, with no rounding or JS number conversion. No new sign restriction is authorized; do not reject a representable negative solely because a lower bound was never specified. Empty clears to null, and `"0.00"` remains a value.

### Calendar-day preservation

`BirthdayPicker.tsx:130-159` makes a local-midnight `Date`, while `useProfileForm.ts:207,269` hydrates a DB date-only string with `new Date(value)` and posts `.toISOString()`. This is a source-derived day-shift risk across timezone offsets. Use a validated `YYYY-MM-DD` calendar string on the wire, construct the picker `Date` from local calendar components on hydration, and serialize local year/month/day rather than an instant. Server validation must reject invalid calendar dates and preserve a nullable birthday. Match the existing age-18 application rule in `profileSchema.ts:66-75`. Astra selected the persisted profile timezone as the shared client/server current-calendar-day basis, with explicit UTC fallback for missing or invalid legacy timezone. For a combined timezone/birthday patch, use the locked pre-update persisted timezone consistently; a later readback supplies the new timezone. Inject the current instant in tests. A February-29 birthday reaches its anniversary on March 1 in a non-leap year (calendar month/day comparison); this defines application validation, not legal-age certification. Test UTC, Africa/Lusaka, and a negative-offset browser zone, including midnight, month/year, leap-day and eighteenth-birthday boundaries.

### Nested JSON preservation

Use an atomic row-locked update (or equivalent single-statement JSONB operation) for nested patch application. `address` and `socialLinks` are JSONB (`shared/schema.ts:283,295`); a full replacement can erase keys the UI does not render, and a read-then-write outside a transaction can lose concurrent edits. A patch should include only changed leaves. Merge supplied leaves with the locked current object, preserving omitted and unknown keys. Explicit `null` clears a supplied optional leaf. For legacy address rows, `useProfileForm.ts:228-239` reads `street -> addressLine1` and `zip -> postalCode`; when the canonical leaf is intentionally changed or cleared, remove its legacy alias in that same update so the old value cannot reappear through the `||` fallback. Preserve legacy aliases when the canonical leaf was omitted. Normalize recognized country names only when they are actually edited. The current converter falls back to `ZM` for unknown names (`useProfileForm.ts:131-145`); replace that silent overwrite with an unchanged legacy value plus a visible explicit-selection path. Unrelated profile edits must leave unknown stored countries untouched.

## API compatibility decision for Astra

The current ProfileForm sends `displayName` and `timezone` only because `transformFormToApiData` spreads its entire hydrated form (`useProfileForm.ts:203-209,263-277`). They are not rendered ProfileForm controls. The only production caller of the profile-update hook found in this source is `useProfileForm`; `client/src/hooks/useAutoSave.ts:31,77` also imports it but `useAutoSave` has test callers only. Display Settings writes its own timezone through `/settings/display` (`DisplayForm.tsx:217-229`). `displayName` and `timezone` remain stored `users` columns (`shared/schema.ts:275,289`) and existing accepted API keys (`settings.validation.ts:8,10`). A route test sends `displayName` in a denied-session case (`server/routes/__tests__/completion-r02.session-access.realdb.integration.test.ts:83`), which does not prove a successful compatibility consumer. `language` is accepted by `settings.validation.ts:11` but is absent from `users` and has no identified production profile PUT caller.

**Astra decision:** make the new ProfileForm client payload strictly the 27 offered controls. Keep `displayName` and `timezone` as *named, validated server compatibility keys*; do not let the new form emit them or infer them from `fullName`. Preserve displayName's existing string/max-50 contract. Validate timezone as a supported IANA identifier within its existing column bound. Reject `language` instead of reporting a successful write with no user column. No generic unknown-key passthrough or silent removal of the two compatibility keys.

### Save lifecycle and unchanged legacy values

- An unchanged form performs no mutation or audit insert and reports no persistence success. The server may reject an empty direct patch; the form never sends it.
- Validate changed offered values against their contracts. Included required keys remain nonempty and valid; hidden fields and omitted invalid legacy values must not block an unrelated patch. Do not silently repair missing fields or unknown countries while saving another field.
- Snapshot submitted values and the verified subject identity. After success, advance the baseline for the submitted values without replacing edits made during the pending save. Failed or uncertain outcomes retain edits. A subsequent Save must include edits made while the first request was pending.
- Preserve session-lifetime fences before query-cache updates, form baseline/reset operations and success feedback. A delayed response belonging to a prior subject cannot update the new subject's cache/form or report success there.

| Save lifecycle | No-op sends nothing; edits made while saving survive; a subsequent save includes them; failures retain edits; old-subject completions do not affect a new subject |
